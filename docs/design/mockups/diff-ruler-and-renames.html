Diff ruler and rename handling

Two changes to the diff pane. The scrollbar becomes a change ruler that marks where every change, review point and thread sits in the file, so you can see the shape of the diff and jump straight to a spot. Renamed files stop showing as a wall of green and instead show the path change, plus only the lines that actually changed.

What the ruler shows

  • Two lanes. Removed lines on the left lane, added lines on the right, so a modification reads as a red and green pair and a pure addition reads as green only.
  • Markers on top. Review points use their existing shape (deviation triangle, correctness octagon and so on), threads a blue dot. Shapes match the gutter markers so meaning never depends on colour alone.
  • Find matches appear as thin yellow ticks while the find bar is open, the same way editors do it.
  • Minimum mark height of 3 px, so a one-line change in a 2,000-line file is still visible and clickable. Marks closer than 2 px merge.
  • The visible area is a soft band. It replaces the scrollbar thumb and can still be dragged.

How you move with it

  • Click a mark to jump. The change lands a quarter of the way down the viewport (same placement as ScrollToLine today) and flashes with the focus colour.
  • Click empty track to scroll there. Drag anywhere to scrub.
  • Hover to see the line range, counts and the first changed line before jumping.
  • ] / [ step to the next or previous change and show “Change 3 of 7” in the header. At the last change, ] moves to the next file. J/K (review points) and N (threads) stay as they are.
  • Split view: one ruler at the far right, covering both sides.

Behaviour

  • Path diff: only the path segments that differ are highlighted, so a folder move and a class rename read differently at a glance.
  • Pure renames are counted with mechanical changes: they don’t ask for review and they sort after real changes, like other mechanical files today.
  • Show file opens the content read-only, with no diff colouring.
  • Comments on a renamed file go to the new path. Threads left on the old path before the move stay attached to this file.
  • Folder move (Case C) groups files that moved from the same folder to the same folder with no content changes. This is optional and can come later.

Why the whole file shows today

The full-PR diff already passes -M, so git detects renames there. The whitespace-ignoring per-file diff (ReviewActions.cs:98) passes only the new path to git diff. Git never sees the old path, so it can’t pair the files and reports the file as added from scratch. The fix is to pass both paths (old and new) for a renamed file, and to keep -M on every diff call, including commit-range views.
